# Part 14 — Deployment: put it on GitHub, then put it on the internet

This part is about shipping the prototype: publishing the repository, hosting a live copy that a
judge can open on a phone, and — just as importantly — being precise about what a hosted copy does
and does not prove.

Read Part 8 first if you only want to run it on your own machine. This part assumes that works.

---

## 0. What gets deployed (one container, two processes)

Everything in this project is designed to fit inside **one** container, which is what makes the
free hosting tiers workable:

| Process | Port | What it is | Reachable from the internet? |
|---|---|---|---|
| Streamlit console | **8501** locally, **7860** on Hugging Face | the investigator dashboard | yes — this is the port that gets proxied |
| FastAPI backend | **8000** | `/alerts`, `/graph`, `/run`, `/upload`, `/ledger/verify` | **no** on Hugging Face (internal only); yes locally |
| uvicorn's Swagger UI | `/docs` on 8000 | interactive API documentation | same as the API |

The dashboard asks the API first (`CHAINTRACE_API_URL`, default `http://127.0.0.1:8000`) and
**silently falls back to reading `data/artifacts/` from disk** if the API is not answering. That
fallback is why the console still works on hosts that can only expose one port — the header just
changes from `API · live` to `artefacts · filesystem`, which is a cosmetic difference, not a
functional one.

Nothing in the running system needs the internet, ever. The image build is the only step that
touches the network, and it uses it for three things: `pip install`, generating the synthetic
dataset, and training the models.

## 1. Choosing where to host it

| Route | Cost | Both processes live? | Sign-in needed | Catch |
|---|---|---|---|---|
| **Hugging Face Space (Docker)** | free, forever, public Spaces | **yes** — the real Dockerfile runs | HF account (email) | one port exposed (7860); disk resets on rebuild |
| **Streamlit Community Cloud** | free | no — dashboard only | GitHub account | no API, no `/docs`; needs the artefacts available at boot |
| **Render free web service** | free | yes | GitHub account | sleeps after ~15 min idle → ~45 s cold start |
| **Local `docker compose`** | free | yes | none | only reachable on the machine running it |

**This project's recommended route is a Hugging Face Docker Space**: it runs the exact image the
README tells judges to build, so the hosted copy and the reproducible copy cannot drift apart, and
both services stay alive.

## 2. GitHub

The repository root is the `chaintrace-ai/` directory itself, so the repository root *is* the Docker
build context — no subdirectory trickery on either host.

```bash
cd chaintrace-ai
git init -b main
git add -A
git commit -m "ChainTrace AI - SIH26146 offline ML triage prototype"

# with the GitHub CLI (creates the remote and pushes in one step)
gh repo create chaintrace-ai --public --source=. --remote=origin --push
```

Without `gh`: create an empty repository in the browser, then

```bash
git remote add origin https://github.com/<you>/chaintrace-ai.git
git push -u origin main
```

### What is in the repository, and what is deliberately not

| Tracked | Ignored | Why |
|---|---|---|
| the whole `src/`, `app/`, `scripts/`, `tests/` tree | `.venv/`, `.venv311/` (~1 GB each) | a virtualenv is not source |
| `data/synthetic/` (the 1,200-transaction dataset + the ground-truth manifest) | `data/artifacts/`, `data/models/*.joblib` | the dataset is the evidence and is byte-stable from `RANDOM_SEED = 42`; the artefacts are regenerated by the build in seconds |
| `data/geo/mock_geoip.json` (offline GeoIP table) | `data/evidence_ledger.jsonl` | regenerated per run |
| the sample upload under `data/raw/upload_*/` | `.env`, `.streamlit/secrets.toml` | never commit secrets |

### CI

`.github/workflows/ci.yml` runs on every push and proves the reproducibility claim on a clean
checkout — no data, no models, no artefacts:

1. `generate_sample_data.py` + `audit_dataset.py` → the dataset still satisfies the SIH26146 contract.
2. `train_models.py` + `run_full_pipeline.py` → all eight stages still run from scratch.
3. `validate_detections.py` → precision/recall against the planted ground truth.
4. `pytest -q` → 60 tests.
5. a second job that builds the real Docker image (no push), so "one command" stays true.

## 3. Hugging Face Space (Docker SDK)

### 3.1 One-time setup

1. Create an account at **https://huggingface.co/join**.
2. **https://huggingface.co/new-space** → name it `chaintrace-ai` → **SDK: Docker** → template
   **Blank** → visibility **Public** → *Create Space*.
3. Create a **write** token: **https://huggingface.co/settings/tokens** → *New token* → type
   **Write**. You will use it for one push and can revoke it immediately afterwards.

### 3.2 Publish

```bash
cd chaintrace-ai

# see what would be published, without publishing
DRY_RUN=1 scripts/deploy_hf_space.sh <your-hf-username>/chaintrace-ai

# publish (token inline; nothing is written to .git/config)
scripts/deploy_hf_space.sh <your-hf-username>/chaintrace-ai hf_xxxxxxxxxxxxxxxxxxxx
```

The script exports **the commit you have checked out** with `git archive`, so uncommitted edits and
ignored files cannot leak into the Space, and it substitutes `deploy/huggingface/README.md` for the
repository README — a Space needs its YAML block at the top of the README, and it verifies the
`sdk: docker` and `app_port: 7860` lines are present before pushing.

Then watch **https://huggingface.co/spaces/&lt;you&gt;/chaintrace-ai/logs**. The build does the
same work as a local `docker compose build`: install the pinned dependencies, generate the dataset,
audit it, train Isolation Forest + LOF, and run one complete pipeline pass. Expect a few minutes;
the Space turns green when it is live.

Live at both of these:

- **https://huggingface.co/spaces/&lt;you&gt;/chaintrace-ai** (the Space page, with the console embedded)
- **https://&lt;you&gt;-chaintrace-ai.hf.space** (the app directly — better on a phone, no iframe)

### 3.3 Revoke the token

Once the build is green, delete the write token. Publishing again later means creating a new one.

## 4. What is different in the hosted copy

Four differences, all handled by `entrypoint.sh` and the `Dockerfile`, and all worth stating out loud
rather than discovering live:

| Difference | Handling |
|---|---|
| Hugging Face proxies **only** the port named by `app_port` (7860) | `entrypoint.sh` picks the port by platform: `CHAINTRACE_DASHBOARD_PORT` if set, else 7860 when `SPACE_ID` is present (which is how a Space identifies itself), else 8501. A local `docker compose up` is unaffected. |
| the container runs as **UID 1000**, not root | the image build chmods the data tree to be writable by anyone. If a host hands us a genuinely read-only tree, the entrypoint copies it to `/tmp/chaintrace-data` and points `CHAINTRACE_DATA_DIR` at the copy, so the ledger and the upload endpoint still work. |
| the Space's disk is **ephemeral** — it resets on every rebuild | the dataset, the trained models and a completed analysis are baked into the image at build time, so the console is never empty on first paint. Only what you write *at runtime* resets (a ledger line appended by the tamper demo, an uploaded file). |
| the FastAPI port is **internal** | everything the dashboard needs is on `127.0.0.1:8000` inside the same container, so it stays `API · live`. Only the Swagger UI at `/docs` is unreachable from outside; run it locally for that (`docker compose up --build` → http://localhost:8000/docs). |

## 5. Verifying a live deployment

Do this after every deploy. It takes thirty seconds and catches the failure mode that matters —
a Space that *looks* green while the console is quietly showing an empty dataset.

```bash
# 1. Streamlit is actually serving (not just "container running")
curl -s https://<you>-chaintrace-ai.hf.space/_stcore/health      # -> ok

# 2. the page returns 200
curl -s -o /dev/null -w '%{http_code}\n' https://<you>-chaintrace-ai.hf.space/

# 3. the build really produced an analysis: from inside the Space, the counters
#    should read 1,200 transactions / 60 alerts, not 0
```

In the browser, the four things worth clicking, in order:

1. **Screen 1** — the counters are non-zero and the ranked alert table is populated; select the
   top alert and read the reasons + recommended action.
2. **Screen 2** — click a node, confirm the halo/focus behaviour, and drag the timeline seek bar.
3. **Screen 3** — the infrastructure roll-up has ASNs and countries, not `unknown`.
4. **Screen 4** — re-verify an alert (hash matches), then run the **tamper demo** and watch the
   ledger reject it.

If counters read zero or the table is empty, the image build did not complete a pipeline pass —
check the Space logs, not the app.

## 6. Updating a deployment

| Host | How to update |
|---|---|
| Hugging Face Space | commit, then `scripts/deploy_hf_space.sh <you>/chaintrace-ai <new-token>` — the Space rebuilds by itself |
| Streamlit Community Cloud | `git push` — it redeploys automatically |
| Render | `git push` — it redeploys automatically |
| Local Docker | `docker compose up --build` |

**Rebuild, do not restart.** The code lives *inside* the image; only `./data` is bind-mounted
(`docker-compose.yml`). Restarting an old container after editing `app/dashboard.py` serves the old
dashboard, which has cost this project an afternoon of debugging a "missing" feature that was right
there in the source. If a change does not appear, the image is stale.

## 7. Cost and limits

| | Hugging Face (CPU basic) | Streamlit Community Cloud | Render free |
|---|---|---|---|
| price | free | free | free |
| RAM / CPU | 16 GB / 2 vCPU | ~1 GB (app-dependent) | 512 MB |
| disk | 50 GB, **not** persistent | not persistent | not persistent |
| sleeps? | after long inactivity | after inactivity | after ~15 min |
| build timeout | 30 min | ~10 min | ~15 min |
| custom Docker | yes | no | yes |

The image needs roughly 600 MB of RAM to run (pandas + scikit-learn + Streamlit + an
Isolation Forest over ~1,200 transactions), so all three tiers are comfortable; if a host is tighter
on memory than expected, lower `MAX_GRAPH_NODES_FOR_EXPORT` / `DEFAULT_TX_COUNT` in `src/config.py`.

## 8. Troubleshooting a deployment

| Symptom | Cause | Fix |
|---|---|---|
| Space builds, then reports *no application is running on port 7860* | the dashboard bound the wrong port | confirm the README's `app_port: 7860` is present (the deploy script checks) and that `SPACE_ID` was not stripped from the environment |
| Space page loads but the iframe is blank | a proxy/CORS mismatch | `.streamlit/config.toml` already sets `enableCORS = false` and `enableXsrfProtection = false`, which is what Streamlit requires behind a reverse proxy; a proxy that also strips websockets will render a blank frame |
| `Permission denied` writing `data/evidence_ledger.jsonl` | the host runs as UID 1000 over a root-owned tree | the `Dockerfile` chmods the tree; if a host overrides that, the entrypoint's `/tmp/chaintrace-data` fallback takes over |
| the build fails at `pip install` | a transient index problem, or the pip cache mount is unsupported | retry; if the builder has no BuildKit, drop the `--mount=type=cache` line from the `Dockerfile` |
| uploaded files vanish after a while | the disk is ephemeral by design | expected — see §4 |
| the console shows `artefacts · filesystem` instead of `API · live` | the API is not answering at `CHAINTRACE_API_URL` | functional, not fatal; check that uvicorn started (it is the first thing `entrypoint.sh` starts) |

## 9. What a deployed copy does *not* prove

Being explicit about this is part of the deliverable:

- **The data is synthetic, and always will be.** A hosted copy proves the pipeline, the models, the
  explanations and the evidence chain work end to end — it proves nothing about real-world
  detection rates, which no synthetic dataset can.
- **The detectors are unsupervised and unlabelled by design.** Precision/recall numbers come from
  the *planted* ground truth in `data/synthetic/planted_patterns.json`, which is a measurement
  harness, not training data. See Part 12 for the honest audit, including the four things it cannot
  show.
- **A hosted console is not an operational system.** No authentication, no multi-analyst case
  management, no chain access, no retention policy. README sections 5 and 17 say the same thing in
  more detail.
- **`localhost` is not a security boundary.** The public Space serves the dashboard over HTTPS, but
  the upload endpoint will accept files from anyone who finds the URL. Take the Space private, or
  run it locally, if that matters for a dry run.
